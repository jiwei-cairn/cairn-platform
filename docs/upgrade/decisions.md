# 升级功能 · 决策清单

> 本文档记录积微 Cairn 升级功能的全部已确定决策，是后续实现与评审的基线。
> 状态：**决策已收齐，待实施**
> 适用范围：微服务（被管服务）的升级，**不含平台自身升级**

## 四、升级行为

| # | 决策项 | 结论 |
|---|---|---|
| D1 | 自动回退 | **不做** |
| D2 | 失败处置 | 告警，**服务保持停止**，由用户决定后续（重新升级到任意版本） |
| D3 | 升级条件 | 目标版本**与当前版本不一致即可升级**（不限升降级方向） |
| D4 | 服务停机 | **允许停止** |
| D5 | 升级方式 | **覆盖**可执行文件 / 配置文件，不保留多版本目录 |
| D6 | 批量升级 | **不做** |
| D7 | 并发升级 | **全局串行排队**：同一时刻只有一个升级任务 |
| D8 | 版本号规范 | **强制语义化版本** `MAJOR.MINOR.PATCH[-pre][+build]` |
| D9 | 导出安装包 | **本轮要做** |
| D10 | 启动后判定 | **不等待**启动结果。启动指令发出后升级任务即结束 |
| D11 | 进程退出等待 | 停服后**等待进程完全退出**再做文件操作；Windows 额外做「可写性探测 + 重试」 |

> **D10 的含义**：升级任务只有两种终态——`success`（换文件完成且启动指令已发出）/ `failed`（任一阶段出错）。
> 服务是否成功运行、后续是否崩溃，**归运行监控负责**，不属于升级业务。

## 五、数据与配置

| # | 决策项 | 结论 |
|---|---|---|
| E1 | 数据备份 | **不做备份** |
| E2 | 数据留存 | 旧版本产生的 `.db` / `log` 等过程文件**留存不丢弃** |
| E3 | 数据可继续使用 | **新版本必须能接着使用旧数据**（见下方承诺边界） |
| E4 | 配置文件策略 | **用最新的**（新版包内配置覆盖） |
| E5 | 配置修改渠道 | 保留既有能力（不改动） |

### E2 + E3 的平台承诺边界

| 平台负责 | 平台不负责 |
|---|---|
| 升级时**绝不触碰** `data/{name}/`，保证旧数据文件原样在 | 新版本**能否正确读取**旧数据（schema 兼容由服务自己保证） |

> ⚠️ **重要说明**：若新版本启动时执行了 schema 迁移，旧数据实际上已被改写，「留存」在语义上即不再是「逐字节原样」。
> 平台不介入服务内部，无法阻止这一点。**服务开发者须自行保证 schema 迁移向后兼容。**

## 六、包格式 `.cairnpkg`（摘要，详见 package-format.md）

| # | 决策项 | 结论 |
|---|---|---|
| F1 | 容器格式 | **ZIP** |
| F2 | 命名约定 | `{name}-{version}-{os}-{arch}.cairnpkg` |
| F3 | 必需首条目 | `manifest.json` 必须是 zip 第一个条目 |
| F4 | 签名 | **本轮不做**。格式中**预留** `signature` 字段（值恒为 `null`），未来启用不破坏兼容 |
| F5 | 文件完整性 | `files[]` 逐文件 `sha256` + `sizeBytes` + `mode` |
| F6 | 版本号 | 强制语义化版本 |
| F7 | 安全约束 | 防 zip slip、防 zip bomb、禁符号链接 |
| F8 | 运行时跳过验签开关 | **不提供**（避免后门） |
| F9 | 主程序路径 | 显式 `entrypoint` 字段，不再靠 `bin/{name}` 推理 |

### F4 的安全边界声明

未启用签名时：

| 威胁 | 能否防 |
|---|---|
| 下载中断导致包不完整 | ✅ 整包 sha256 校验 |
| 传输中损坏 | ✅ 同上 |
| **有意的包伪造** | ❌ 无法防 |
| **服务器被入侵后替换包** | ❌ 无法防 |

> **现阶段安全依赖「服务器可控 + 网络可信」**。该前提在自建内网场景可接受。
> **一旦开始向客户现场交付，必须补上签名。** 详见 `package-format.md` 的签名预留章节。

## 十、排队模型

| 项 | 结论 |
|---|---|
| 模型 | **全局串行**：单队列，同一时刻仅一个升级任务 |
| 选择理由 | ① 边缘设备 IO / 内存有限 ② 不做批量升级，并行收益小 ③ 微服务有依赖关系，串行天然安全 ④ 断电恢复简单 |
| 卡死防护 | 每个任务设超时（默认 10 分钟），超时即失败并释放队列 |

## 十一、`.old` 过渡文件

**产生原因**：Windows 无法覆盖运行中的 exe（已实测证实），只能「重命名 → 放入新文件」。若在放置新文件后、删除 `.old` 前断电，则残留。

| 项 | 结论 |
|---|---|
| 升级成功 | **立即删除** `.old` |
| 平台启动时 | **扫描并删除**所有残留 `.old`（此时服务必然未运行，安全） |
| 跨平台 | Linux 也采用同一逻辑（虽然 Linux 可直接覆盖），保持实现统一 |

## 十二、签名策略（本轮不做，未来实施）

**结论：本轮不实现签名，但格式预留字段，且预留多公钥 + 多签名能力。**

### 为什么必须现在就预留

平台已决定**不做平台自升级**。这意味着：

> 信任的公钥列表一旦编译进设备，未来**无法通过平台升级来更换**。

因此必须现在就设计成支持多公钥（`keyId` 查表）+ 多签名（双签过渡），否则未来轮换密钥将无解。

### 未来实施的三阶段（备忘）

| 阶段 | 做法 |
|---|---|
| 1. 开发期 | 生成 dev 密钥对，私钥本地保管且**不入库**（`.gitignore`） |
| 2. 首次正式发布 | 生成正式密钥；用**双签**过渡（dev + release 同时签），设备用任一可信公钥验签即可 |
| 3. 长期运维 | 新密钥**只新增不删除**；旧密钥退役但保留在信任列表（老设备仍需验旧包） |

### 硬性约束（未来实施时必须遵守）

| 约束 | 理由 |
|---|---|
| 私钥**绝不入库** | 泄露 = 全线沦陷 |
| 不提供 `--skip-verify` 运行时开关 | 后门 |
| 签名对象 = 剔除 `signature` 后的规范化 manifest JSON | zip 元数据不稳定，签整包会导致同内容不同机器验签失败 |
| 公钥硬编码进二进制 | 配置文件可被篡改 |
| 信任列表支持多条目 | 密钥轮换的唯一途径 |

## 十三、实施顺序

```
第 0 步  包格式规范定稿（本文档 + package-format.md）
第 1 步  目录扁平化 + 工作目录移到 data/{name}/        ← 阻塞项，改动最大
第 2 步  部署流水线（install / upgrade 共用）+ 版本号规范化校验
第 3 步  导出安装包（闭环出口）
第 4 步  本地 Web 升级（打通换文件主链路 + 断电恢复）
第 5 步  OTA（拉清单 + 下载，复用第 4 步换文件逻辑）
第 6 步  清理 USB 残余代码
```

**顺序理由**：包格式不定 → 导出无依据 → 升级无输入 → OTA 无内容。必须自上而下。
